# Phase 9: Ship — packaging, CI, docs, Python removal

## Overview

Publish the Rust implementation to crates.io and npm with prebuilt binaries,
update the documentation to describe reality, and remove the Python source now
that it has served its purpose as the porting oracle.

This phase contains a **breaking change**: `pip install mystquarto` and
`uvx myst2quarto` stop working. That was an accepted decision, and it needs to
be communicated, not buried.

> **Red team RT-04, RT-16 applied.** The original phase justified deleting the
> Python source with "git history retains everything" in a directory that is not
> a git repository; treated live PyPI users as speculative when the package has
> three published releases; scheduled the deprecation release *after* deleting
> `pyproject.toml`; published crates that make the documented
> `cargo install mystquarto` fail; and accepted a generated release workflow
> holding publishing tokens with no provenance, pinning, or scope reservation.

## Requirements

- Functional: `cargo install mystquarto` yields working binaries.
- Functional: `npx mystquarto` runs without a global install.
- Functional: GitHub releases carry prebuilt binaries for macOS (arm64, x64),
  Linux (x64, arm64, musl), and Windows (x64).
- Functional: `src/mystquarto/` and `tests/*.py` removed; `pyproject.toml` gone.
- Non-functional: the breaking change is stated in README, CHANGELOG, and the
  release notes.

## Architecture

### Distribution

| Channel | Mechanism | Install |
|---|---|---|
| crates.io | `cargo publish` — `mystquarto-core`, then the **`mystquarto`** crate | `cargo install mystquarto` |
| npm | wrapper resolving a platform-specific optional dependency | `npx mystquarto` |
| GitHub Releases | `cargo-dist` cross-compile matrix, with checksums | direct download / installer script |

`cargo install` resolves a **package** name. Phase 3 renames the CLI crate to
`mystquarto` for exactly this reason; publishing `mystquarto-core` +
`mystquarto-cli` would have made every documented install command fail.

npm is the right second channel for this audience: MyST *is* a Node application
(`myst` is installed via npm) and Quarto users routinely have Node. The wrapper
package publishes `@mystquarto/darwin-arm64`, `@mystquarto/linux-x64` and so on
as `optionalDependencies` gated by `os`/`cpu`, with a thin `bin` shim that execs
the resolved binary. This is the standard pattern (esbuild, swc) and avoids a
postinstall download.

`cargo-dist` generates the release workflow, the cross-compile matrix, and the
installer scripts, so the binary matrix is configuration rather than hand-written
CI.

### Python removal

Removal happens **after** Phase 8 is green **and after both preconditions**, not
before. The Python implementation is the oracle for the parity tier, and deleting
it early destroys the ability to answer "what did the old one do here?".

**Precondition 1 — version control.** The original rationale, "git history
retains everything else; removal is recoverable," was false: `git rev-parse` at
the project root returns `fatal: not a git repository`. Phase 1 establishes the
repo and a tagged pre-port commit; deletion is gated on that tag existing.

**Precondition 2 — PyPI deprecation.** `mystquarto` is **live on PyPI** with
releases 0.1.0, 0.1.1, 0.1.2 — not the speculative user base the original risk
section assumed. `README.md` documents `pip install mystquarto` and
`uvx myst2quarto docs/`. Publish a final PyPI release whose description points at
the Rust install methods **before** deleting `pyproject.toml`, otherwise the
mitigation is unschedulable — the original step order made it impossible to
execute.

Delete: `src/mystquarto/`, `tests/*.py`, `tests/conftest.py`,
`tests/fixtures/`, `pyproject.toml`, `uv.lock`, the Python CI job.

Keep: `tests/corpus/` — it is now Rust-native data, and it holds the
`python-actual.*` records, which preserve the old behavior as documentation
without keeping the code.

## Implementation Steps

1. Set crate metadata: description, license (MIT-0), repository, keywords,
   categories. Verify **and reserve** `mystquarto` on crates.io and npm **and
   every `@mystquarto/<triple>` platform scope**. Reserving only the root name
   leaves `optionalDependencies` open to a dependency-confusion takeover of an
   `npx`-executed native binary — the attacker controls what runs, not just what
   installs.
2. Configure `cargo-dist`; **review** the generated release workflow rather than
   accepting it as-is: scope `permissions:` narrowly, pin every third-party
   action to a commit SHA, and use trusted publishing (OIDC) instead of
   long-lived crates.io/npm tokens. Verify the matrix on a tag in a fork first.
3. Build the npm wrapper and platform packages with `--provenance`; publish
   checksums for the GitHub release binaries. Test `npx` from a clean cache on
   macOS and Linux.
3b. Confirm the Phase 1 pre-port tag exists, then publish the final PyPI
   deprecation release pointing at the Rust install methods.
4. Write `CHANGELOG.md` for 0.2.0. Lead with the breaking change: Python
   distribution is discontinued; `pip`/`uvx` no longer work; here is the
   replacement command.
5. Write `docs/migration-from-python.md`: install changes, behavior changes from
   the modern-MyST decision, new diagnostics, the sidecar file, and how to
   suppress it.
6. Rewrite the README: Rust install paths, the IR architecture, `cargo` dev
   commands, and a link to `docs/dialect-comparison.md`. The current
   "No heavy dependencies — just click + pyyaml" architecture paragraph is
   entirely obsolete.
7. Delete the Python implementation and its CI job.
8. Tag and publish: crates.io (core, then cli), npm, GitHub release.
9. Verify from a clean machine or container: `cargo install`, `npx`, and a
   downloaded binary each convert `article-template/` correctly.

## Risk Assessment

**Risk: the name or a platform scope is taken on npm.** All are currently free,
but the `@mystquarto/*` scope is what the binary resolution depends on.
*Signal:* step 1 lookup fails for the root name **or any platform scope**.
*Response:* if the root name is taken, fall back to `@mystquarto/cli` and keep
the crates.io name. If the **scope** is taken, the platform-package scheme fails
with it — switch to a different scope entirely and rename all platform packages
together. Resolve at step 1, before any packaging work depends on the name.

**Risk: users depend on the Python package.** Not speculative — PyPI serves
`mystquarto 0.1.2` today, and `README.md:8,14` documents `pip install` and `uvx`.
*Signal:* already realized; treat as certain.
*Response:* step 3b publishes a final deprecation release pointing at the Rust
install methods, before `pyproject.toml` is deleted. Leaving 0.1.2 as the last
PyPI version makes it a permanent trap serving all 16 defects with no forward
pointer.

**Risk: deleting Python loses undocumented behavior.** The 225 tests may not
cover everything the implementation does.
*Signal:* post-release reports of behavior that used to work.
*Response:* recoverability comes from the Phase 1 tag, not from an assumption —
the original "git history retains everything" was false here. Plus the corpus
retains `python-actual.*` for every defect case. With the tag in place this is
low severity and does not justify a second implementation.

**Risk: cross-compilation fails for musl or Windows.** These targets routinely
surface linker issues.
*Signal:* matrix failures at step 2.
*Response:* ship the targets that build, and file the rest as follow-up. Do not
block the release on a complete matrix — the primary platforms are macOS and
Linux x64/arm64.
